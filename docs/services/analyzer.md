# Сервис `analyzer`

Оценивает транскрипт по карточке этапов и промпту проекта. Запись не слушает. В CRM не ходит.

В запрос входят три части. Постоянная системная инструкция задаёт JSON и администратором не редактируется. Карточка этапов и промпт администратора передаются данными, а не продолжением инструкции. Туда же уходят утверждённые факты продукта, менеджер и клиент этого звонка и вся стенограмма. Сценарий менеджера и анкеты покупателей не отправляются. Телефон, сделка, заметка и произвольные поля записи в модель не уходят. Стадия сделки промпт не выбирает.

Модель — внешний API, задаётся окружением (`LLM_MODEL`, ключ). Своя языковая модель в контейнере не запускается. Какую модель поставить в окружение, выбирают позже по качеству оценки на потраченные деньги. Имя провайдера эти документы не задают, на сборку ядра это не влияет.

Вызов делает один общий HTTP-клиент chat-completions. Он лежит в общем пакете репозитория, из сервисов его вызывает только `analyzer`. Клиент передаёт `response_format: { "type": "json_object" }`, ограничивает ожидание таймаутом и сам другую модель не подставляет. Ответ не разбирается мягко: JSON не вырезается из текста и не чинится. В `call_analysis.ai_model` пишется имя модели, которая фактически ответила.

Итог и покрытие считает сервис. Поле итога в ответе модели игнорируется.

```text
quality_score = round(100 × Σ(weight × score / 4) / Σ(weight))
```

В обе суммы входят только этапы со статусом `scored`. Все четвёрки дают 100. `not_applicable` не входит ни в балл, ни в покрытие. `unobservable` из балла исключён и стоит в знаменателе покрытия:

```text
coverage = Σ(weight scored) / Σ(weight scored + weight unobservable)
```

Пустой знаменатель — `null`, не 0. Если есть `unobservable`, итог предварительный. Веса берутся из карточки в момент обработки и сохраняются в снимке. Позже правка настроек готовый итог не меняет. Флаги нарушений балл не меняют.

## Вход

Очередь `calls.analyze`:

```json
{
  "message_id": "uuid",
  "project_id": "uuid",
  "call_id": "uuid",
  "attempt": 1,
  "enqueued_at": "2026-10-13T12:06:00+03:00"
}
```

Из базы собирается пакет для модели. В очередь он не кладётся. Системное сообщение — фиксированная инструкция формата. Пользовательское сообщение — JSON с данными:

```json
{
  "scorecard": {
    "key": null,
    "stages": [
      {
        "key": "opening",
        "title": "Открытие",
        "weight": 15,
        "high_score": "Начало разговора и установление контакта",
        "defect_example": "",
        "sample_line": ""
      }
    ]
  },
  "prompt": "Как ставить 0–4, not_applicable и unobservable.",
  "product_facts": "Утверждённые факты или пустая строка.",
  "manager": { "name": "Анна" },
  "client": { "name": "Алексей", "company": null },
  "transcript": [
    { "id": "t1", "speaker": "manager", "start": 0.0, "end": 4.5, "text": "Добрый день..." }
  ]
}
```

`stages` равен текущей карточке проекта, а не зашитым ключам. Пример выше показывает форму запроса. Пустой промпт и пустые факты допустимы.

В модель уходит весь транскрипт: реплики всех говорящих, с их `id`. Роли сохраняются. Неуверенность в ролях оценку не останавливает.

Снимок ушедших данных пишется в `call_analysis.inputs_json`. Сценарий из `project_inputs` в снимок не входит.

Если снимок этапов уже записан, модель не вызывается. Итог при этом может быть пустым: все этапы неприменимы.

В начале работы статус `analyzing`. Одновременно не больше `ANALYZE_CONCURRENCY` заданий. Это потолок провайдера оценки: сколько запросов он принимает сразу. Число задаётся окружением. Делёж слотов между проектами — в [архитектуре](../architecture.md).

Ответ модели — только JSON. Текст вне JSON считается ошибкой ответа. Даже если промпт просит другой формат, код проверяет тот же контракт.

```json
{
  "stages": [
    {
      "key": "S1",
      "status": "scored",
      "score": 4,
      "reason": "Роль названа в начале",
      "evidence_ids": ["t1"]
    },
    {
      "key": "S2",
      "status": "not_applicable",
      "score": null,
      "reason": "Этому разговору этап не нужен",
      "evidence_ids": []
    }
  ],
  "flags": [
    { "code": "false_role", "evidence_ids": ["t1"] }
  ],
  "payment_agreement": {
    "agreed": false,
    "summary": null,
    "evidence_ids": []
  }
}
```

Набор ключей совпадает с карточкой. `status` — `scored`, `not_applicable` или `unobservable`. У `scored` балл целое 0–4, у остальных `score` пустой. `reason` не пустой. Каждый `evidence_id` есть в этой стенограмме. У флага есть хотя бы один такой id. Если договорённость `agreed: true`, у неё тоже есть id реплики. Поля `quality_score`, `coverage` и любой итог модели игнорируются.

## Выход

Та же строка `call_analysis`:

| Поле | Откуда |
| --- | --- |
| `stages_json` | ключ, название, вес и тексты карточки плюс статус, балл, обоснование и id реплик |
| `summary` | строка `summary` из ответа, если модель её прислала; иначе пусто |
| `overall_score` | `quality_score` |
| `extras_json` | покрытие, предварительность, флаги, договорённость об оплате |
| `ai_model` | имя модели, которая фактически ответила |
| `created_at` | время успешной записи |

Пример баллов 4, 3, 4, 3, 3, 4, 2, 4 и весов 5, 10, 10, 15, 10, 20, 15, 15:

```text
quality_score = round(100 × 83.75 / 100) = 84
```

После записи `calls.processing_status=completed`. Следующей очереди нет.

## Ошибки

| Ситуация | Результат |
| --- | --- |
| нет транскрипта | повтор, затем `failed`, `error.stage=analyze`, `error.message=transcript_missing` |
| нет карточки этапов | повтор, затем `failed`, `error.stage=analyze`, `error.message=scorecard_missing` |
| модель недоступна | повтор, затем `failed`, `error.stage=analyze`, `error.message=model_unavailable` |
| ответ не JSON, другой набор ключей, чужой id реплики, балл не 0–4, статус не из трёх, флаг без реплики | повтор, затем `failed`, `error.message=invalid_model_json` |

Невалидный JSON и неполный набор этапов не превращаются в частичный результат. Из такого ответа в строку не попадает ничего. Этап повторяется, затем статус `failed`.
