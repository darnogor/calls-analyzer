# Сервис `analyzer`

Оценивает транскрипт по промпту проекта и скриптам. Запись не слушает. Имена, сделку, заметку и произвольные поля звонка в модель не передаёт. В CRM не ходит.

Модель — внешний API, задаётся окружением (`LLM_MODEL`, ключ). Своя языковая модель в контейнере не запускается. Какую модель поставить в окружение, выбирают позже по качеству оценки на потраченные деньги. Имя провайдера эти документы не задают, на сборку ядра это не влияет.

Вызов делает один общий HTTP-клиент chat-completions. Он лежит в общем пакете репозитория, из сервисов его вызывает только `analyzer`. Клиент передаёт `response_format: { "type": "json_object" }`, ограничивает ожидание таймаутом и сам другую модель не подставляет. Ответ не разбирается мягко: JSON не вырезается из текста и не чинится. В `call_analysis.ai_model` пишется имя модели, которая фактически ответила.

Итог считает сервис:

```text
overall = round(сумма по этапам: score * weight)
```

Веса берутся из карточки проекта в момент этой обработки и сохраняются в снимке. Позже правка настроек готовый итог не меняет.

## Вход

Очередь `calls.analyze`:

```json
{
  "message_id": "uuid",
  "project_id": "uuid",
  "call_id": "uuid",
  "attempt": 1,
  "enqueued_at": "2026-10-13T12:06:00+03:00"
}
```

Из базы собирается пакет для модели. В очередь он не кладётся.

```json
{
  "scripts": [
    {
      "title": "Исходящий первый звонок",
      "body": "Представиться, назвать компанию, спросить, удобно ли говорить."
    }
  ],
  "transcript": [
    {
      "speaker": "manager",
      "start": 0.0,
      "end": 4.5,
      "text": "Добрый день, Алексей..."
    }
  ],
  "stages": [
    {
      "key": "opening",
      "title": "Открытие",
      "weight": 0.15,
      "instruction": "Начало разговора и установление контакта"
    },
    {
      "key": "needs",
      "title": "Потребность",
      "weight": 0.30,
      "instruction": "Выявление ситуации, проблемы и критериев выбора"
    },
    {
      "key": "presentation",
      "title": "Презентация",
      "weight": 0.20,
      "instruction": "Конкретность предложения под сказанное клиентом"
    },
    {
      "key": "objections",
      "title": "Возражения",
      "weight": 0.20,
      "instruction": "Работа с возражениями, включая стоимость"
    },
    {
      "key": "closing",
      "title": "Закрытие",
      "weight": 0.15,
      "instruction": "Зафиксирован ли следующий шаг"
    }
  ]
}
```

`scripts` — все текущие скрипты проекта. Выбора скрипта для одного звонка нет. Пустой список допустим: тогда оценка идёт только по промпту и транскрипту. Список `stages` равен промпту проекта, а не зашитым пяти ключам. Пример этапов выше — шаблон нового проекта.

В модель уходит весь транскрипт: реплики всех говорящих, не только менеджера. Роли в репликах сохраняются. Неуверенность в ролях оценку не останавливает.

Тот же список скриптов сервис пишет в `call_analysis.inputs_json`. Позже правка скрипта этот снимок не меняет. Поля записи в снимок не входят.

Если `overall_score` уже заполнен, модель не вызывается.

В начале работы статус `analyzing`. Одновременно не больше `ANALYZE_CONCURRENCY` заданий. Это потолок провайдера оценки: сколько запросов он принимает сразу. Число задаётся окружением. Делёж слотов между проектами — в [архитектуре](../architecture.md).

Полный текст системной инструкции в эти документы не входит. Ответ модели — только JSON по ключам переданных этапов. Текст вне JSON считается ошибкой ответа. Клиент не вырезает JSON из текста и не чинит ответ.

```json
{
  "stages": {
    "opening": { "score": 85, "comment": "Хорошо установил контакт" },
    "needs": { "score": 70, "comment": "Выявил проблему, но не выяснил критерии выбора" },
    "presentation": { "score": 68, "comment": "Презентация слишком общая" },
    "objections": { "score": 55, "comment": "Слабо отработал возражение по стоимости" },
    "closing": { "score": 60, "comment": "Не зафиксирован следующий шаг" }
  },
  "summary": "Клиент заинтересован. Основная потребность выявлена."
}
```

Набор ключей в ответе совпадает с набором ключей запроса. `score` — целое 0–100. `comment` и `summary` не пустые. Поле итога в ответе модели игнорируется. Отдельного признака следующего шага в ответе нет: это видно из оценки и комментария этапа «Закрытие».

## Выход

Та же строка `call_analysis`:

| Поле | Откуда |
| --- | --- |
| `stages_json` | ключ, название, вес и формулировка из запроса, оценка и комментарий из ответа |
| `summary` | `summary` |
| `overall_score` | формула весов |
| `ai_model` | имя модели, которая фактически ответила |
| `created_at` | время успешной записи |

Пример шаблона и оценок 85, 70, 68, 55, 60:

```text
overall = round(85*0.15 + 70*0.30 + 68*0.20 + 55*0.20 + 60*0.15)
        = round(67.35)
        = 67
```

После записи `calls.processing_status=completed`. Следующей очереди нет.

## Ошибки

| Ситуация | Результат |
| --- | --- |
| нет транскрипта | повтор, затем `failed`, `error.stage=analyze`, `error.message=transcript_missing` |
| модель недоступна | повтор, затем `failed`, `error.stage=analyze`, `error.message=model_unavailable` |
| ответ не JSON, другой набор ключей, пустые `comment` или `summary`, оценка вне 0–100 | повтор, затем `failed`, `error.message=invalid_model_json` |

Невалидный JSON и неполный набор оценок не превращаются в частичный результат. Недостающие этапы не отбрасываются, чтобы записать остальные: из такого ответа в строку не попадает ничего. Этап повторяется, затем статус `failed` и `error.message=invalid_model_json`.
