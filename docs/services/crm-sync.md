# Сервис `crm-sync`

Единственный сервис, который вызывает amoCRM API v4. Забирает пользователей, примечания звонков, контакты, компании, сделки и справочник стадий. Обновляет access token через refresh token.

Аудио не скачивает, речь не распознаёт, оценки не ставит.

## Вход

### 1. OAuth

Браузер открывает:

```http
GET /oauth/amocrm/start
GET /oauth/amocrm/callback?code={code}&state={state}
```

На `start` сервис перенаправляет на страницу разрешения amoCRM. На `callback` меняет `code` на токены и пишет строку `accounts`. Сразу после первой успешной записи токенов публикует сам себе две команды: `sync_reference` и `import_history`.

Секрет клиента OAuth и redirect URI приходят из переменных окружения контейнера.

### 2. Webhook

```http
POST /webhooks/amocrm
```

Тело — формат webhook amoCRM о новом или изменённом примечании. Сервис сохраняет тело в `amo_events` со `source=webhook` и `process_status=pending`, ставит сообщение в `crm.events` и отвечает `200` пустым телом. Разбор в этом HTTP-запросе не выполняется.

Если секрет пути не совпал (отдельный token в URL или заголовке, конкретная схема — после проверки кабинета amoCRM), ответ `401`, событие не пишется.

Сообщение `crm.events` от webhook:

```json
{
  "message_id": "uuid",
  "amo_event_id": "uuid",
  "attempt": 1,
  "enqueued_at": "2026-10-05T20:15:00+03:00"
}
```

### 3. Резервный опрос

Внутренний таймер раз в `poll_interval_sec`. Сервис запрашивает у amoCRM примечания `call_in` и `call_out` за окно `poll_lookback_sec` и на каждое новое примечание пишет `amo_events` со `source=poll` и такое же сообщение в `crm.events`.

### 4. Команды от `api` и собственные

Очередь `crm.commands`:

```json
{
  "message_id": "uuid",
  "command": "sync_reference",
  "enqueued_at": "2026-10-05T20:15:00+03:00"
}
```

`command`:

| Значение | Кто ставит | Что сделать |
| --- | --- | --- |
| `sync_reference` | `api` или сам `crm-sync` после OAuth | пользователи, воронки, статусы, текущие стадии уже известных сделок |
| `import_history` | сам `crm-sync` один раз после OAuth | звонки за `import_days` |

Повторный `import_history`, если `history_imported_at` уже заполнен, команда помечается выполненной и звонки заново не создаёт.

### 5. Ответы amoCRM

Входные объекты API, которые сервис обязан уметь прочитать:

- пользователь: `id`, `name`, `email`, `rights.group_id` или аналог группы, признак активности;
- примечание звонка: `id`, `note_type` (`call_in` или `call_out`), `entity_id`, тип сущности (`contacts`, `leads`, `companies`), `created_by`, `responsible_user_id`, `params.uniq`, `params.duration`, `params.link`, `params.phone`, `params.source`, `params.call_responsible`;
- контакт с вложенными сделками и компанией;
- сделка с вложенными контактами;
- компания с вложенными контактами;
- воронки и статусы, включая признак успешного и проигранного статуса.

Точные JSON-поля amoCRM сверяются на технической проверке одного звонка. Если имени поля в ответе нет, сервис оставляет соответствующую нашу колонку пустой и продолжает по правилам ниже.

### 6. Настройки и словарь добавочных

Перед фильтром длительности читает `settings.min_call_duration_sec`. При поиске менеджера читает `telephony_extensions`.

## Выход

### Справочники

`sync_reference` перезаписывает `managers` по `amo_user_id`: имя, почта, группа, активность. Пользователя, исчезнувшего из amoCRM, не удаляет, ставит `is_active=false`.

Тот же проход обновляет `pipelines` и `pipeline_statuses`.

Для каждого звонка, у которого заполнен `amo_lead_id`, обновляет `current_deal_status_id` и `current_deal_status_name`. Поля `deal_status_at_call_*` этим проходом не меняются.

Обновляет `accounts.last_user_sync_at`. Опрос обновляет `accounts.last_poll_at`. Успешный импорт истории пишет `accounts.history_imported_at`.

### Решение по одному примечанию

На сообщение из `crm.events` сервис загружает примечание через API, если в журнале ещё нет полного тела.

Дальше по порядку:

1. `note_type` не `call_in` и не `call_out` — событие `ignored`, звонок не создаётся.
2. `duration` меньше `min_call_duration_sec` — событие `ignored`, звонок не создаётся.
3. Уже есть звонок с тем же `(account_id, external_call_id)` — событие `processed`, новая строка не создаётся. Если у существующего звонка статус `recording_pending` и в примечании появился `link`, публикуется задание на скачивание (шаг 8).
4. Создаётся или обновляется контакт по правилам привязки.
5. Определяется сделка.
6. Определяется менеджер.
7. Пишется строка `calls`. Стадия сделки в этот момент копируется и в `deal_status_at_call_*`, и в `current_deal_status_*`.
8. Если `params.link` не пустой — статус `audio_queued` и публикуется `calls.audio.fetch`. Если ссылки нет — статус `recording_pending` и планируется повторное чтение примечания.

`external_call_id` равен `params.uniq`. Если `uniq` пустой, равен строковому `amo_note_id`.

`direction`: `call_in` → `in`, `call_out` → `out`.

### Менеджер

Первое сработавшее правило:

1. `responsible_user_id` примечания, если такой пользователь есть в `managers`.
2. `params.call_responsible`, если это числовой id пользователя amoCRM и он есть в `managers`.
3. `created_by`, если есть в `managers`.
4. Совпадение `params.phone` или добавочного из `params.source` со строкой `telephony_extensions`.

Найденный id пишется в `calls.amo_user_id` и `calls.manager_id`. Если не найдено ни одно правило, оба поля пустые, звонок всё равно обрабатывается.

### Контакт и компания

Родитель примечания:

| Родитель | Действие |
| --- | --- |
| контакт | читаем контакт со сделками, сохраняем `amo_contact_id`, имя, компанию |
| сделка | читаем сделку с контактами, берём главный контакт, сохраняем его так же |
| компания | читаем компанию и связанные контакты; если контакт один — сохраняем его; если контактов несколько или ноль — `contact_id` пустой, в отдельное поле звонка компания не дублируется, название компании остаётся пустым на экране |

Главный контакт сделки — контакт, которого amoCRM помечает главным. Если метки нет и контакт один, берём его. Если меток нет и контактов несколько, `contact_id` пустой.

### Сделка

Первое сработавшее правило:

1. Примечание само прикреплено к сделке — берём её. `deal_link_status=linked`.
2. У контакта ровно одна активная сделка — берём её. `deal_link_status=linked`.
3. У контакта несколько активных сделок — `amo_lead_id` пустой, `deal_link_status=ambiguous`.
4. Иначе `amo_lead_id` пустой, `deal_link_status=unresolved`.

Активная сделка определяется по справочнику статусов: статус не успешный и не проигранный.

При `linked` заполняются `pipeline_id`, `deal_name`, `deal_price`, оба набора полей статуса.

### Повторное чтение записи

Для статуса `recording_pending` сервис снова запрашивает примечание через `recording_recheck_delays_sec` (1, 5 и 15 минут от создания строки).

Появился `link` — статус становится `audio_queued` и публикуется сообщение ниже. Три интервала прошли без ссылки — `processing_status=recording_missing`, очередь `calls.audio.fetch` не вызывается.

### Сообщение `calls.audio.fetch`

Публикуется, когда у звонка есть непустой `recording_source_url` и ещё нет `recording_storage_key`.

```json
{
  "message_id": "uuid",
  "call_id": "uuid",
  "attempt": 1,
  "enqueued_at": "2026-10-05T20:15:00+03:00",
  "source": {
    "type": "url",
    "url": "https://telephony.example/recordings/abc"
  }
}
```

`source.type=url` — скачать файл по адресу. Поле зарезервировано под второй тип, когда появится телефония без прямой ссылки:

```json
{
  "source": {
    "type": "telephony",
    "provider": "имя-провайдера",
    "external_id": "id-записи-у-провайдера"
  }
}
```

Пока вопрос о телефонии открыт, `crm-sync` публикует только `type=url`.

### Импорт истории

`import_history` выбирает `call_in` и `call_out` за последние `import_days`, прогоняет каждый через те же правила, что и одно событие, и публикует `calls.audio.fetch` только для прошедших фильтр. Параллельность распознавания и оценки ограничивают уже `transcriber` и `analyzer`, не этот сервис.

### Ошибки

Ошибка API amoCRM на разборе одного события: три попытки сообщения `crm.events`, затем `amo_events.process_status=failed`. Строка `calls` при этом может уже существовать. Если карточка звонка создана, а следующий шаг не опубликован, статус звонка `failed`, `error.stage=resolve`.

Истёкший access token обновляется один раз и запрос повторяется. Повторный отказ обновления токена останавливает и разбор событий, и таймеры до нового OAuth. В `GET /api/integration` это видно как подключенный аккаунт с устаревшим `last_poll_at`; отдельный код ошибки интеграции добавим, когда будет ответ на вопрос о настройках.
